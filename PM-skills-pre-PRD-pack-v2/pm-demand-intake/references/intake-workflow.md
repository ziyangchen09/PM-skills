# 需求受理工作流

## 第一步：保留原始输入

保存：

- 原始文字；
- 来源类型；
- 提出人；
- 时间；
- 原始链接或本地路径；
- 是否为转述；
- 是否包含附件、截图或数据。

转述内容必须标记为转述，不得视为目标用户原话。

## 第二步：拆分输入

将输入拆为：

| 项目 | 含义 |
|---|---|
| 表面诉求 | 对方直接要求做什么 |
| 目标候选 | 对方希望改善什么结果 |
| 用户候选 | 谁实际使用或受影响 |
| 场景候选 | 在什么任务和条件下发生 |
| 问题候选 | 当前可能存在的障碍 |
| 方案成分 | 输入中已经指定的功能或实现方式 |
| 约束 | 时间、合规、技术、商业或组织条件 |

只要来源没有直接支持，就使用“候选”“可能”“待验证”。

## 第三步：检索历史

优先检索：

1. 相同功能名和别名；
2. 相同用户任务；
3. 相同问题或异常表现；
4. 已确认决策；
5. 已归档 PRD；
6. 已知缺陷；
7. 相关反馈。

输出结果只能标记为：

- 直接重复；
- 部分重叠；
- 可能相关；
- 存在冲突；
- 未发现相关资料。

没有找到不等于不存在。

## 第四步：评估证据

证据等级：

| 等级 | 含义 |
|---|---|
| E0 | 没有直接证据，仅有想法或要求 |
| E1 | 单一主观反馈、转述或个例 |
| E2 | 多个一致反馈，或一个明确场景的详细证据 |
| E3 | 行为、日志、数据、流程观察或稳定复现支持 |
| E4 | 多来源交叉验证，且存在反例检查或定量结果 |

不得为了提高等级而重复计算同一来源。

## 第五步：选择下一步

### 进入问题定义

适用于：

- 已存在可描述的用户、场景或障碍；
- 输入仍主要是功能要求，但需要追溯真实问题；
- 影响和目标尚未被清楚定义。

### 用户研究或数据验证

适用于：

- 核心用户和场景无法识别；
- 只有主观结论，缺乏行为证据；
- 不同来源明显冲突；
- 需求价值高度依赖未经验证的假设。

### 缺陷处理

适用于：

- 当前行为违反已确认需求、设计或验收标准；
- 问题可以稳定复现；
- 不需要重新做产品价值判断。

如果“预期行为”本身未确认，不得直接判定为缺陷。

### 复用已有能力

适用于：

- 已有功能能够闭环解决；
- 主要问题是入口、配置、培训、权限或认知；
- 新开发不会增加实质价值。

### 技术预研

适用于：

- 核心不确定性是模型、性能、硬件、接口或数据可行性；
- 产品价值基本清楚，但实现能力未知。

### 暂缓

适用于：

- 影响极低且无时间敏感性；
- 当前存在更高优先级阻塞；
- 缺乏最低限度信息，且暂时无法补充。

暂缓必须记录原因和重新评估条件。

## 默认只问一个必要问题

只有当问题会改变当前主路径时才提问，例如：

- 这是哪个产品或项目？
- 反馈来自实际使用者还是内部转述？
- 当前表现违反的是哪条已确认规则？

其他缺口先记录，不连续追问。

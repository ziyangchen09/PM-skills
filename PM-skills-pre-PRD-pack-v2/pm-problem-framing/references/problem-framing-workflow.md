# 问题定义工作流

## 1. 方案剥离

把输入中的解决方案改写为待分析问题。

示例：

```text
原始诉求：增加一个历史结节按钮。
```

拆分为：

```text
方案：新增历史结节入口。
问题候选：用户可能难以找到或定位历史结节。
待验证：困难发生在哪一步、影响谁、频率和后果是什么。
```

不得删除原始方案，它仍是后续候选方案之一。

## 2. 当前任务链

按实际顺序描述：

```text
触发
→ 用户进入任务
→ 查找所需信息
→ 判断或操作
→ 提交或确认
→ 获得结果
```

每一步标记：

- 使用对象；
- 所需信息；
- 当前系统支持；
- 人工绕行；
- 失败方式；
- 产生的成本或风险。

## 3. 障碍定位

障碍可以属于：

- 找不到；
- 看不懂；
- 不知道下一步；
- 操作成本高；
- 信息不完整；
- 状态不清；
- 系统结果不可信；
- 需要跨系统；
- 权限受限；
- 性能或稳定性不足；
- 容易出错；
- 无法恢复；
- 不满足合规或审计要求。

“体验差”“效率低”“不方便”必须继续拆解为可观察障碍。

## 4. 影响分析

优先使用可观察影响：

- 任务完成时间；
- 操作步骤；
- 重复劳动；
- 错误或遗漏；
- 决策延迟；
- 用户放弃；
- 沟通成本；
- 交付成本；
- 合规和安全风险；
- 收入或续约影响。

没有数据时只描述影响方向，不虚构数值。

## 5. 原因分析

建立原因假设表：

| 原因假设 | 支持证据 | 反例 | 可信度 | 验证方式 |
|---|---|---|---|---|

只在来源直接支持时标记为“已证实”。

## 6. 目标状态

目标状态描述用户或业务结果，不预设具体界面：

正确：

```text
医生能够在会诊过程中快速定位同一病灶的历史影像，并确认匹配关系。
```

错误：

```text
系统增加一个蓝色历史结节按钮。
```

## 7. 问题陈述

使用：

```text
对于【目标用户】，
在【具体场景】下，
当其需要完成【任务】时，
由于【当前障碍】，
导致【可观察影响】。

我们希望使【任务或结果】达到【目标状态】，
本次暂不处理【非目标】。
```

## 8. 问题拆分

满足任一条件时拆分：

- 不同用户的目标不同；
- 不同场景的触发和流程不同；
- 障碍需要不同证据验证；
- 问题可以独立解决和验收；
- 一个问题属于产品，另一个属于技术、流程或培训。

不要把一个端到端问题机械拆成多个页面问题。

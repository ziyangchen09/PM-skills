# 方案比较规则

## 比较维度

使用高、中、低或明确说明，不强制伪精确分数。

| 维度 | 判断重点 |
|---|---|
| 问题覆盖度 | 解决主问题还是只缓解症状 |
| 用户价值 | 对任务效率、质量、安全或结果的改善 |
| 证据匹配度 | 方案是否建立在当前证据支持的原因上 |
| 实现复杂度 | 产品、设计、研发、测试和上线成本 |
| 使用成本 | 用户学习、操作、迁移和维护成本 |
| 技术风险 | 性能、稳定性、兼容性和可行性 |
| 数据或算法风险 | 数据质量、效果、漂移和评估口径 |
| 合规与安全 | 隐私、审计、医疗或业务安全 |
| 外部依赖 | 团队、系统、供应商、接口和硬件 |
| 可逆性 | 失败后是否容易回退 |
| 可维护性 | 长期规则、配置、运维和技术债 |
| 扩展性 | 是否支持后续场景而不过度设计 |

## 推荐原则

优先考虑：

- 直接解决主问题；
- 关键假设更少；
- 能快速验证价值；
- 高风险点可控；
- 可以复用已有能力；
- 失败后可回退；
- 不锁死未来方案。

不得因为实现成本低，就推荐只能遮盖症状的方案。

## 放弃理由

放弃方案时写明属于：

- 问题覆盖不足；
- 证据不支持；
- 成本与当前价值不匹配；
- 风险不可控；
- 依赖未满足；
- 过度设计；
- 当前阶段不适合；
- 可作为后续演进。

不要使用“方案不好”这类不可追溯表述。

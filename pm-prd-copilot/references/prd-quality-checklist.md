# PRD 审查清单

只报告会影响决策、实现或验收的问题。

## 产品

- 用户、场景和问题是否有证据。
- 目标、成功指标与非目标是否清楚。
- 范围、优先级和依赖是否一致。
- 业务规则是否存在冲突或未定义边界。

## 流程与 UI

- 入口、退出、返回、取消和重复操作是否定义。
- loading、空、失败、无权限、离线和极端数据状态是否覆盖。
- 默认值、选中态、禁用态和响应式规则是否明确。
- 文案、反馈时机、键鼠操作和可访问性是否可实现。

## 用户故事与场景

- 只为不同的角色、目标或触发场景拆分故事；合并同一用户目标下的 UI 操作步骤。
- 角色、目标和价值是否来自原始输入或可追溯资料；不确定时标为假设或待确认。
- 每个核心故事是否至少有一个正常场景，并按需覆盖空/边界、失败/恢复和权限差异。
- `Given` 是否只写前置状态，`When` 是否只有一个关键触发，`Then` 是否是可观察、可测试的结果。
- 不得用“系统正常处理”等不可验收表述，也不得为了凑齐场景而补造业务规则。

## 研发

- 状态来源、保存时机、并发和幂等规则是否明确。
- API、数据模型、权限、兼容性和性能边界是否明确。
- 与既有功能、历史数据、埋点和第三方依赖是否冲突。
- 灰度、迁移、回滚和异常恢复是否可执行。

## 验收

- 每条核心需求是否有可观察结果。
- 正常、异常、边界和权限场景是否可测试。
- 待确认项是否有负责人或决策条件。

## 生成评审预判

1. 先检索历史资料。已有明确答案时写成带来源的约束，不再提问；新旧信息冲突时才列为问题。
2. 每个问题必须来自原文、历史冲突或明确缺失字段，并说明不确认会造成的实现或返工影响。
3. 研发问题聚焦状态归属与保存、数据/API、权限、并发幂等、兼容性能、迁移回滚、异常恢复和可测试性。
4. UI 问题聚焦入口与层级、默认/选中/禁用状态、操作反馈、文案、空/错/loading/无权限、极端数据、响应式和可访问性。
5. 同一问题只保留一次；跨团队问题指定共同确认人。建议回答必须标为建议，不得伪装成已确认结论。
6. 删除不会改变产品决策、实现方案或验收结果的泛化问题。

## 输出格式

```text
问题 | 等级 | 依据 | 影响 | 建议 | 需谁确认
```

等级：

- `P0 阻塞`：缺少后无法实现或验收，或存在明确的数据、安全、合规风险。
- `P1 高风险`：可以开始，但大概率造成核心逻辑返工或跨端行为不一致。
- `P2 优化`：不阻塞交付，用于改善易用性、表达或实现质量。

# 原型视觉设计

本参考只补足视觉流程，不改变 PRD、数据口径或交互业务规则。原型仍使用项目现有 Vue/CSS/组件体系；不为更换样式引入新的前端框架。

## 按模式工作

### preserve：沿用样式

先读 `design/context.md`、已有样式规范和上一版本，复用现有变量、组件和布局。只做任务直接需要的变化，不生成候选风格，不因为某个设计技能偏爱特殊字体、配色或动效而重设计。

### refine：局部视觉升级

先列明调整范围和保持不变项，再优化该区域的层级、字重、留白、表格密度、控件状态或对齐。具体反馈可直接执行；只有存在实质性方向分歧时才比较小范围方案，不为一次按钮间距修改启动完整视觉探索。

### explore：全新视觉探索

1. 从 PRD 和用户指令明确目标用户、主任务、使用设备、信息密度、风格约束和不可变项。已有明确答案直接复用，只补会影响方向的缺口。
2. 用户没有给定视觉目标时，先做一个代表页面的 2–3 个方向。差异应体现在信息层级、布局、密度或操作组织，不能只换主题色；使用相同脱敏业务数据便于比较。
3. 需要图像方案且 Product Design 可用时，读其 `ideate`，按其规则生成并交给用户选择，再由 `image-to-code` 实现。概念图不能当作已验证可交互页面。用户已有选定图稿、Figma 或明确设计方案时跳过探索。
4. 用户选择前保留提案，不展开其余页面。用户已明确授权自主选型时，按该授权决定并记录依据，不重复索取批准；调用的专用技能若有必须选择的规则，按该技能处理。
5. 把选定方案的变量和组件状态记录到本版 `visual-spec.md`，再实现完整主流程。

## 设计技能怎么接入

每次只选当前任务需要的能力，不串行加载全部设计技能。

| 能力 | 何时使用 | 如何使用 |
| --- | --- | --- |
| `ui-ux-pro-max` | 新方案缺少配色、排版、密度或组件规则依据 | 从当前可用技能目录定位真实 `scripts/search.py`；检索与实际产品匹配的条目 |
| `frontend-design` | 探索新视觉、建立版式与风格方向 | 读当前已安装版本；先做业务适配的变量和版式方案，再实现 |
| `impeccable` | 已有页面需要评审或精修 | 使用已安装版本提供的 critique / polish / typeset / layout / quieter 指导，限定修改范围 |
| Product Design | 需要可见方案比较、按图实现 | 按 `ideate` → 选定视觉 → `image-to-code` 流程，不把整页生成图嵌入页面充当实现 |

技能未安装或不可用时，基于项目现有规范继续可完成的工作并记录缺口；不要伪称已经调用，也不自动安装或升级依赖。

UI UX Pro Max 的命令以实际技能目录为准；先查看 `--help`，不要照抄另一个平台的 `.claude/skills` 路径：

```powershell
python -X utf8 "<ui-ux-pro-max技能目录>/scripts/search.py" "enterprise medical imaging workstation dense table" --design-system -p "<project-id>" -f markdown
python -X utf8 "<ui-ux-pro-max技能目录>/scripts/search.py" "forms table accessibility" --stack vue
```

这些是设计建议，不是医学证据或已确认规范。不要把通用 healthcare 推荐的诊所营销页、SPA 配色或大幅宣传首屏套在阅片工作台上。生成时默认只读取输出，把采用的值写入本版提案；不直接用 `--persist` 覆盖共享规范。

## 保存选定设计

- `design/context.md`：可追溯的已有事实、推断和未知项；由上下文技能维护。
- `prototypes/<requirement-id>/vNNN/visual-spec.md`：本版新规则或偏离项，写明提案/已选定状态、来源及本轮确认依据。纯功能修改可以不新建。
- `design/style-guide.md`：用户确认可在项目复用的规则；没有新选择时复用，不每轮重建。
- `design/pages/<page-id>.md`：确有页面差异时才建立，只写已确认的覆盖项和适用范围。

本版提案至少明确：背景/表面/文字/边框/主操作/选中/风险的语义色；中文字体及回退、标题/正文/标签/数值的字号字重行高；间距、圆角、布局和表格密度；本次涉及控件的默认、悬停、焦点、禁用、处理中、错误及选中状态。只记录当前任务真正用到的规则，不搭建完整组件库。

将实际采用的变量落在现有 CSS 变量或项目 token 中，避免说明文件与渲染值各一套。规范中标明来源、适用范围、确认依据和对应原型版本。局部例外不反向覆盖全项目。

## 业务系统与医学影像适配

- 企业操作界面优先可扫描、稳定位置和任务密度；营销/展示界面才按任务需要增强视觉表达。
- 中文字体优先保证本机可用和长时间阅读，可使用合适的系统中文字体；不要机械套用英文标题字体或外链字体。检查中英文、单位、数值和长标签混排。
- 表格使用一致的行高与列对齐，数值按需使用等宽数字。宽表可在自身容器横向滚动；不得把主要操作挤出可用区域。信息密度变化不能以隐藏关键字段为代价。
- 风险、选中、处理中、禁用等含义分别定义；风险不能只靠颜色表达，需要文字或图标辅助。不擅自改变已确认的风险分级与颜色语义。
- 深色阅片区与信息面板按真实使用场景设计，不以纯黑/渐变的通用审美禁令覆盖已有工作台。检查暗底上的小字、分隔线、焦点和叠加控件。
- 组件样式比较固定业务数据、窗口尺寸和未调整背景。仅在整体探索允许的范围改变背景，并明确说明。
- 主操作保留清晰文字标签；图标操作有可访问名称和可见提示，键盘焦点可见。保留必要的状态反馈，尊重减少动效设置。

## 看实际页面再验收

1. 构建后在浏览器打开本轮原型，确认页面和资源加载成功，再实际操作主流程及本轮涉及的弹窗、抽屉、筛选或表单。
2. 桌面页面检查目标尺寸及一个较窄窗口，例如 1440 和 1024 像素；根据设备约束调整。PRD 包含移动端时再检查相应尺寸，不强制把桌面工作台改造成手机页面。
3. 检查长中文、长数值、空数据、加载、失败、选中、禁用等适用状态；核对层级、文字截断、局部滚动、遮挡、语义颜色、键盘焦点及可访问名称。
4. 将截图保存在本版 `screenshots/`，记录视口、页面状态、操作结果和与参考的偏离。一次集中修正已发现问题，再复核受影响场景。
5. 在 `prototype.md` 分别记录构建、实际渲染、实际交互；浏览器不可用或某状态没有执行时写“未验证”和原因，不用静态代码检查代替。
